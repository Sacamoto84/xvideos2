# A4: учёт находок ревью

> **Для агентных исполнителей:** ОБЯЗАТЕЛЬНЫЙ СУБ-НАВЫК: используйте
> `superpowers:executing-plans`. Шаги размечены чекбоксами (`- [ ]`).

**Цель:** сделать так, чтобы ответ на вопрос «что из найденного ревью закрыто, а
что нет» читался за минуту, а не собирался чтением семи документов и git log.

**Архитектура:** в `docs/` лежат шесть отчётов о ревью (проходы 1-6 плюс
проход от 2026-08-16), четыре плана и несколько справочных документов. Формат
учёта статусов у каждого свой: где-то раздел «Статус исправлений», где-то
blockquote в шапке, где-то таблица «Найдено / Исправлено», а где-то ничего.
Индекса нет. Один документ — `docs/hardening-plan.md` — уже содержит образцовую
таблицу «находка → коммит»; она и берётся за общий формат.

Задача чисто документационная: кода не меняет, тестов не добавляет. Единственная
проверка — что все ссылки в индексе ведут туда, куда обещают.

**Стек:** Markdown.

**Радиус:** A1, A2, A3 — отдельные планы. Содержание самих отчётов не
переписывается: правится только шапка со статусом и добавляется индекс.

### Задача 2: Единая шапка статуса в отчётах

Сейчас статус находок в отчётах оформлен четырьмя разными способами. Приводим к
одному: сразу после заголовка идёт блок из трёх строк — срез, статус, ссылка на
следующий проход. Содержание отчёта ниже не трогаем.

**Файлы:**
- Изменить: шапки пяти файлов `docs/CODE_REVIEW_*.md`

- [ ] **Шаг 1: Определить фактический статус каждого отчёта**

Для каждого отчёта прочитать существующий раздел о статусе и понять, все ли
находки закрыты:

```bash
grep -n -i "статус\|исправлен\|закрыт\|не сделан\|открыт" docs/CODE_REVIEW_2026-07-30.md | head -20
```

Повторить для остальных четырёх. Выписать: «закрыт полностью» / «закрыт
частично, открыто: …».

- [ ] **Шаг 2: Вставить единый блок**

В каждый из пяти файлов сразу после строки заголовка (`# Код-ревью …`) вставить
блок по образцу:

```markdown
> **Срез:** `<коммит>` · **Статус:** закрыт · **Индекс:** [все документы](README.md)
```

Для частично закрытых:

```markdown
> **Срез:** `<коммит>` · **Статус:** закрыт частично — открыто: <перечисление>
> · **Индекс:** [все документы](README.md)
```

Существующие разделы «Статус исправлений» внутри документов **оставить**: они
содержат детали по пунктам, которых в шапке нет. Шапка — это оглавление
статуса, а не его замена.

- [ ] **Шаг 3: Сверить с индексом**

Статусы в шапках и в таблице `docs/README.md` обязаны совпадать. Пройти по
таблице и проверить каждую строку. Расхождение здесь — ровно та проблема,
которую A4 и решает.

- [ ] **Шаг 4: Коммит**


### Задача 3: Шаблон следующего отчёта

Формат разъехался потому, что каждый следующий отчёт писался «по образцу
предыдущего, но чуть иначе». Шаблон закрепляет минимум, без которого отчёт
нельзя считать законченным.

**Файлы:**
- Создать: `docs/CODE_REVIEW_TEMPLATE.md`

- [ ] **Шаг 1: Написать шаблон**

Создать `docs/CODE_REVIEW_TEMPLATE.md`:

```markdown
# Код-ревью xvideos — проход N

> **Срез:** `<коммит>` · **Статус:** открыт · **Индекс:** [все документы](README.md)

База прохода `<коммит>`, за проход <N> коммитов, <N> файлов, +<N> / −<N>.
Линзы: <перечислить углы зрения, если проход шёл линзами>.

## Находки

Идентификатор находки — буква класса и номер: `S` безопасность, `C`
корректность, `T` конкурентность и жизненный цикл, `A` архитектура. По этим
идентификаторам находка потом трассируется в план и в коммит.

### S1 — <заголовок>. <Серьёзность>.

<Файл и строка ссылкой>. Что не так, почему это дефект, что произойдёт у
пользователя. Если находка воспроизводится — как именно.

## Статус

| Находка | Класс | Статус | Коммит |
| --- | --- | --- | --- |
| S1 | безопасность | закрыт | `<sha>` |
| A1 | архитектура | открыт, план: [ссылка](.) | — |

## Проверка

```
<команды и их результат>
```

## Что осталось открытым

Находки без плана — с причиной, почему их не закрыли: цена, риск, ожидание
решения. Пустой раздел лучше отсутствующего: он означает «проверено, ничего не
осталось».
```
