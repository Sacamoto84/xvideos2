## Находки

### C1 — Декларативное разделение BackHandler в экране-камуфляже калькулятора. Средняя.

[app/src/main/java/com/client/xvideos/calculator/CalculatorScreen.kt:59-70](file:///g:/xvideos2/app/src/main/java/com/client/xvideos/calculator/CalculatorScreen.kt#L59-L70)

В `CalculatorScreen` использовался императивный `BackHandler` без условия `enabled`, внутри которого проверялись условия стирания цифр, сброса операций и выхода:
```kotlin
BackHandler {
    when {
        state.displayValue == CalculatorState.ERROR_TEXT || (!state.isNewEntry && state.displayValue != "0") -> {
            state.onBackspace(haptic)
        }
        !state.isAllClear -> {
            state.onClear(haptic)
        }
        else -> onBack()
    }
}
```
Так как обработчик был зарегистрирован постоянно активным, системный диспетчер навигации и механизм предиктивного жеста назад (Predictive Back) в Android не могли заранее определить, будет ли жест назад поглощён экраном или приведёт к выходу.

**Решение:**
1. Разделено на три декларативных `BackHandler` с вычисленными предикатами активности:
   ```kotlin
   val canBackspace = state.displayValue == CalculatorState.ERROR_TEXT || (!state.isNewEntry && state.displayValue != "0")
   val canClear = !canBackspace && !state.isAllClear

   BackHandler(enabled = canBackspace) {
       state.onBackspace(haptic)
   }
   BackHandler(enabled = canClear) {
       state.onClear(haptic)
   }
   BackHandler(enabled = !canBackspace && !canClear) {
       onBack()
   }
   ```
2. В `CalculatorStateTest.kt` добавлен модульный тест проверки корректности переходов состояний `canBackspace`, `canClear` и системного выхода при различных фазах ввода и вычислений.

### C2 — Риск коллизии ключей в LazyVerticalGrid коллекций. Средняя.

[feature-l/src/main/java/com/client/xvideos/l/ui/screens/explorer/tab/saved/collection/CollectionsGrid.kt:64-70](file:///g:/xvideos2/feature-l/src/main/java/com/client/xvideos/l/ui/screens/explorer/tab/saved/collection/CollectionsGrid.kt#L64-L70)

В сетке `CollectionsGrid` ключи элементов задавались как `key = { it.name }`. При наличии локальных или импортированных коллекций с одинаковыми именами (или временными дубликатами данных) Compose LazyLayout выбрасывал критическое исключение `IllegalArgumentException: Key is already used`.

**Решение:**
1. Сетка переведена на `itemsIndexed` с составным уникальным ключом по индексу:
   ```kotlin
   itemsIndexed(collections, key = { index, item -> "${item.name}#$index" }) { _, collection ->
   ```
2. Одиночный элемент добавления новой коллекции переведён с `items(listOf(Unit))` на каноничный `item { ... }`, устраняя лишнюю аллокацию списка при рекомпозиции.

### C3 — Риск коллизии ключей в диалоге добавления в коллекцию L_DialogCollection. Средняя.

[feature-l/src/main/java/com/client/xvideos/l/ui/screens/explorer/L_DialogCollection.kt:100-108](file:///g:/xvideos2/feature-l/src/main/java/com/client/xvideos/l/ui/screens/explorer/L_DialogCollection.kt#L100-L108)

В диалоговом окне выбора коллекции `L_DialogCollection` в `LazyColumn` ключ формировался исключительно из строкового имени `key = { index -> savedL.collection.collectionList[index].collection }`. При дублировании названий коллекций происходил краш Compose рендерера.

**Решение:**
Ключ защищён суффиксом индекса:
```kotlin
key = { index -> "${savedL.collection.collectionList[index].collection}#$index" }
```
