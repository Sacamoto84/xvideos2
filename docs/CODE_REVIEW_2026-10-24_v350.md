# Код-ревью xvideos — проход 217 (v350)

> **Срез:** `a5fa70cd` · **Статус:** открыт (T1, T2 закрыты в `4db887d1`) · **Индекс:** [все документы](README.md)

Аудит производительности Compose по официальному скиллу Google
`jetpack-compose-performance` (репозиторий `android/skills`, версия от
22.10.2026). Прошлые проходы смотрели производительность попутно; это первый
проход, где она — единственная линза. Код не менялся, проход — только чтение.

Охват — `src/main` всех шести модулей: 517 файлов с `@Composable`, около
56 тысяч строк. Сначала поиск по 35 шаблонам, разложенным по семи категориям
скилла, затем каждое попадание прочитано в коде. Скилл требует перед каждой
находкой читать его справочник по категории — все шесть справочников
прочитаны до разбора.

Версия Compose в релизе — **1.12.1** (сверено по `release-mergeJavaRes`
от 22.10). Отсюда два следствия для правок: `computedStateOf` из скилла
недоступен (он с 1.13) — вместо него `remember { derivedStateOf { … } }`;
`SideEffect(key)` есть (проверено по исходникам runtime 1.12.1).

Линзы — категории скилла:

1. состояние, фазы и стабильность: чтение быстро меняющегося состояния в
   композиции, обратная запись, `derivedStateOf`, `snapshotFlow`, коллекции
   состояния, `@Stable`/`@Immutable`;
2. разметка: `onGloballyPositioned`, сабкомпозиция, intrinsic-замеры;
3. ленивые списки: `key` и `contentType`, поиск по списку в элементе, выбор,
   `CompositionLocal` и подписки внутри элементов;
4. анимации: чтение анимированного значения в композиции, лямбды-поставщики;
5. эффекты и потоки: `LaunchedEffect` без приостановки, пустой `onDispose`,
   ввод-вывод на главном потоке, форматтеры в теле, таймеры;
6. графика: аллокации в отрисовке, загрузка растровых ресурсов, `Pair` и
   упаковка в горячих циклах;
7. `Modifier.composed` против `Modifier.Node`;

и базовые требования скилла: релизная сборка, R8, baseline profiles.

Ни одна находка не замерена: в проекте нет ни макробенчмарка, ни baseline
profile (A1). Серьёзность оценена по частоте работы — каждый кадр, 20 раз в
секунду, на событие, — а не по миллисекундам.

## Находки

Идентификатор находки — буква класса и номер: `S` безопасность, `C`
корректность, `T` конкурентность и жизненный цикл, `A` архитектура. По этим
идентификаторам находка трассируется в план и в коммит, поэтому менять их
задним числом нельзя. Находки производительности, как в проходе 199, идут под
`T` с классом «производительность» в таблице статуса.

### T1 — Временная диагностика `LDIAG` в ленте картинок L работает в релизе на каждом кадре прокрутки. Средняя.

[L_LazyRowPictureDetails.kt:81](../feature-l/src/main/java/com/client/xvideos/l/ui/element/lazyRowPictureDetails/L_LazyRowPictureDetails.kt:81)

Коммит `fa6dbb29` добавил `LaunchedEffect` со `snapshotFlow` по
`gridState.layoutInfo.visibleItemsInfo`. Комментарий — «TEMP … не
коммитить», сообщение коммита — «убрать после разбора сдвигов». Блок
выполняется на каждый кадр прокрутки ленты деталей альбома L и на каждый
видимый элемент:

- `map { Triple(k, y, h) to lane }` — `Triple`, `Pair` и упаковка четырёх
  `Int`;
- `it.key.toString().substringAfterLast('#')` — две строки;
- три `HashMap.put` с упаковкой ключей и значений;
- аргументы `Timber.w(…)` — массив varargs с упакованными числами, а
  `joinToString` строит строку до вызова.

В релизе дерево Timber не посажено
([App.kt:101](../app/src/main/java/com/client/xvideos/App.kt:101)): записей
в журнале нет, но все аллокации остаются. Это правило скилла о `Pair`/`Triple`
и строках в горячих циклах (категория 6): на 15–20 видимых карточках — сотня с
лишним объектов на кадр, и сборщик мусора срабатывает прямо во время
прокрутки.

Что делать: убрать блок, когда разбор сдвигов закончен. Если он ещё нужен —
не выполнять его в релизной сборке.

Чего нет: аллокации не профилировались, просадка кадров не измерялась —
вывод сделан по чтению кода.

### A1 — Нет baseline profile и макробенчмарка. Средняя.

[app/build.gradle:105](../app/build.gradle:105)

Из трёх базовых требований скилла два выполнены: релиз собирается с R8
(`minifyEnabled`, `shrinkResources`, `proguard-android-optimize.txt`),
профилировать советуют только его. Третьего нет — baseline profile для
холодного старта и прокрутки лент. Файлов `baseline-prof.txt` в модулях нет,
модуля генерации тоже. Без профиля ART после установки исполняет код ленты
интерпретатором и JIT, пока фоновая компиляция не соберёт профиль сама.
Первые прокрутки после установки и обновления — самые медленные.

Второе следствие: этот отчёт нечем подтвердить цифрами. Макробенчмарк с
двумя сценариями — холодный старт и прокрутка ленты X, R или L — дал бы и
профиль, и замер «до/после» для T1–T16.

Решение за владельцем: это новый модуль сборки и сценарии UI Automator, а не
правка.

### T3 — Логотип экрана замка декодируется с увеличением на главном потоке. Низкая.

[AppLockHeader.kt:33](../core/src/main/java/com/client/xvideos/common/applock/atom/AppLockHeader.kt:33) ·
`core/src/main/res/drawable/logo.png`

`Image(painterResource(R.drawable.logo))` при `Modifier.size(88.dp)`.
Ресурс — PNG 512×512 на 296 КБ в папке `drawable/` без плотности, то есть
mdpi. `painterResource` берёт bitmap через `Resources.getDrawable` (сверено
по исходникам ui 1.12.1), а тот масштабирует mdpi под экран. На 420–480 dpi
это ~1350–1536 px по стороне, 7–9 МБ ARGB. Ради кадра в 88dp (~230–264 px)
синхронный декод идёт в композиции экрана замка — на первом показе за
процесс, то есть на холодном старте с включённым замком.

Правило скилла (категория 6): растровые картинки — не через
`painterResource`. Варианты: векторный логотип; PNG нужного размера в
`drawable-nodpi`; `AsyncImage` из Coil, который уже в проекте.

Чего нет: время декода и пик памяти не измерены. Плотность экрана телефона
владельца не проверена.

### T9 — Полоса прокрутки: позиция считается асинхронно, на каждый кадр — `Pair`. Низкая.
