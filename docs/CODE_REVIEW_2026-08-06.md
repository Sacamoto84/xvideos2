# Проход 5: четыре линзы

Линзы: границы после распила · свежий поиск R · что происходит при отказе ·
время жизни и ресурсы.

## Что исправлено

### 1. Ошибка сети превращалась в пустую ленту без права на повтор (`9d84a3e`)

Главная находка прохода. `cacheMediaResponse` при отказе сети возвращал

```kotlin
return MediaResponse(0, 0, 0, emptyList(), emptyList(), emptyList(), emptyList())
```

— пустой объект вместо ошибки. Дальше по цепочке `pages = 0` превращались в
`nextKey = null`, и Paging получал **успешную пустую страницу**: `LoadState.Error`
не наступал, кнопки «повторить» не было, экран показывал пустоту.

Задеты все кешируемые ленты: Week, Month, Trending и ниши. При этом соседний
`getTopLatest` шёл через `Result` и ошибку показывал честно — то есть приложение
вело себя по-разному в зависимости от выбранной сортировки, и заметить это можно
было, только переключив сортировку при выключенной сети.

`cacheMediaResponse` теперь возвращает `Result<MediaResponse>`, следом переведены
восемь методов, оба источника пагинации снимают результат одним `getOrThrow()`.

Попутно в тех же местах:

- **пропущенный `return`** в ветке `FORCE_TEMP` у `ItemNailsPagingSource`:
  `LoadResult.Page` создавался и выбрасывался, выполнение шло дальше и уходило в
  сеть с пустым `order`. То есть «Refresh» в нишах делал обычный запрос
  неизвестно с какой сортировкой. detekt такое не ловит;
- битая запись кеша больше не роняет запрос: удаляется, запрос идёт в сеть;
- `GsonBuilder().create()` собирался на каждый запрос — стал один на модуль;
- откат `else -> getTopThisWeek` оставлен, но пишет предупреждение.

### 2. Выбранная сортировка молча заменялась на Latest (`33a5628`)

Набор сортировок в ленте гифок стал разным без поиска и с поиском — второй
появился в `41402ec`, за день до этого прохода. `All time` есть только в первом,
`Relevant` и `Top` — только во втором, поэтому выбранное значение стало из набора
выпадать. Обрабатывал это `SortByOrder` одной строкой:

```kotlin
if (!list.any { it == selected }) { onSelect(Order.LATEST) }
```

Два дефекта в одной строке. Вызов `onSelect` стоит прямо в composition —
побочный эффект в отрисовке. И сброс идёт на самое далёкое от выбора значение.

Сценарий: поставить «All time», написать слово, убрать фокус. `AnimatedVisibility`
снова компонует `SortByOrder`, в наборе поиска `All time` нет — поиск уходит с
«Latest», без единого сообщения. Меняется не только подпись: `sortType` входит в
`combine`, собирающий Pager, поэтому лента ещё и перезапрашивалась и уезжала в
начало.

- вызов уехал в `LaunchedEffect(list, selected)`;
- вместо жёсткого `LATEST` — `Order.nearestIn`: All time → Top, Relevant →
  Trending, Top → Week. Замены попадают только в значения, проверенные на
  устройстве (`docs/redgifs-api.md`);
- набор сортировок ключуется на `searchTextDone`, а не на отображаемом тексте:
  по `searchText` список дёргался с первого символа, до подтверждения ввода.

`OrderNearestInTest` держит соответствие и проверяет, что результат всегда лежит
в наборе — иначе `LaunchedEffect` зациклится.

### 3. Кеш ответов R не истекал никогда (`7bf15d0`)

`FileStringCacheTable` писал `timeCreate` с самого начала, но никогда его не
читал, а `deleteOld` не вызывался ниоткуда. Следствий два: лента не обновлялась
(«Топ за неделю», однажды попавший в кеш, показывался бы и месяц спустя), и
папка росла без потолка — ключ там полный URL вместе с номером страницы.

- у таблицы появился `ttlMs`; по умолчанию `null` — прежнее бессрочное
  поведение, четыре остальные таблицы не задеты;
- `get()` не отдаёт просроченное и удаляет его;
- `deleteExpired()` подметает каталог целиком — `get()` чистит только те записи,
  за которыми пришли, и мусор от лент, куда больше не заходят, так и лежал бы;
- `now` вынесен параметром, чтобы не спать в тестах;
- `deleteOld(timeMs)` удалён: вызовов не имел, две почти одинаковые ручки, одна
  из которых мёртвая, — приглашение позвать не ту.

Срок для `rCacheMediaResponse` — шесть часов. Уборка вызывается из
`MainActivity`, из фонового `launch(Dispatchers.IO)` рядом с
`VideoDiskCacheCleaner`, а не из `initApp()`: ту ждут перед открытием главного
экрана, а здесь обход каталога неизвестного размера.

## Что нашёл и не стал чинить

**`Order.TOP_ALLTIME` без своей ленты.** `ItemTopPagingSource` уводит его в
`else` и отдаёт `getTopThisWeek` — то есть «All time» без поиска показывает
неделю. Значение `alltime` на устройстве не проверялось, а неверный `order` у
RedGifs не даёт ошибки (приходит чужая выдача), поэтому метод не заводился:
проверить догадку можно только глазами. Записано в `docs/redgifs-api.md`, откат
в `else` теперь пишет предупреждение, `nearestIn` туда никого не приводит сама.

**Дырявое кодирование URL.** `Route.encodeURIComponent` — 21 ручной `replace`.
Не экранируются `%`, кириллица и `{`/`}`; подстановка идёт `replace("{ключ}", …)`
по порядку, и текст поиска `{order}` попал бы в результат и был бы заменён
следующей итерацией. Замена — `URLBuilder` из Ktor, он уже в зависимостях.
Оставлено: правка сетевого слоя целиком, отдельно от этого прохода.

**Мёртвый код в сетевом слое.** `searchCreators` (обе перегрузки) и
`searchTagsShort` не вызываются ниоткуда. Во второй перегрузке в URL есть
`count={count}`, а параметра `count` в `routeParams` нет — плейсхолдер уехал бы в
запрос буквально. Ровно тот класс дефекта, что чинили в `9a646e1` и `705c6c4`:
сломано молча, потому что не вызывается.

Линзы: разбор X · слой L · время жизни корутинных скоупов · безопасность ·

## Что исправлено

### 1. Разбор страниц X молчал вместо того, чтобы сообщать об отказе (`a35c689`)

Три места, где неудача выглядела как успех с пустыми данными.

**Признак отказа — строка `"null"`.** `parserVideoPreviewFromImageUrl` возвращал
её при неудаче. Проверял её один вызывающий из трёх, поэтому она ложилась в
`ItemsX.previewVideo` и возвращалась туда же на следующем экране: разбор снова
давал `"null"`, откат `?: item.previewVideo` доставал из модели ту же строку.

До плеера это не доходило — `UrlVideoLite.normalizedPreviewUrlOrNull` в `:core`
отсеивает `"null"` и пустое последним рубежом. **В первой редакции отчёта я
написал, что в плеер уходит адрес из четырёх букв; это неверно.** Правка всё
равно сделана: признак отказа, про который обязаны знать три слоя и который
защищён только в самом конце, надо убирать типом. Теперь `null` — его нельзя
забыть проверить.

**Позиционный селектор.** `parserItemVideo` брал скрипт по месту:
`#video-player-bg > script:nth-child(6)`. Шестой по счёту. Один лишний тег выше —
`select` возвращает пустую коллекцию, `html()` отдаёт пустую строку, разбор идёт
дальше как ни в чём не бывало. Ищем по содержимому (`html5player.`), контейнер
остаётся предпочтительным, но при смене разметки обходим все скрипты страницы.

**Пустой конфиг.** `parseHTML5Player` при полном промахе возвращал
`HTML5PlayerConfig` со всеми полями `""`. Теперь `null`, если не нашлось ни
одного источника — ни low, ни high, ни HLS. Все три вызывающих уже работали с
nullable, правка для них прозрачна.

`XParsersTest` — двенадцать проверок. До него весь разбор X не был покрыт ничем,
хотя это единственный слой, который ломается от чужих правок на стороне сайта,
без предупреждения и без единой ошибки в логе.

### 2. Compose в слое данных L и мёртвый `Saver` (`3dd0c55`)

`Repository` держал `protectionUiState` через `mutableStateOf` —
snapshot-состояние Compose в слое данных, и писалось оно из фоновых корутин.
Сторож слоёв этого не видит: он сравнивает только импорты своего раздела и про
`androidx.compose` ничего не знает. Теперь `StateFlow`.

`DefaultPagerState1.Saver` был объявлен и не использовался ни разу: состояние
живёт в `ScreenAlbumListSM`. Хуже, что при восстановлении он подставлял
`updatedPageCount = { it[2] as Int }` — лямбду-константу, — и число страниц
замерло бы на сохранённом. Удалён, чтобы его не подключили однажды по имени.

Стартовое число страниц у пейджера было `10` — заглушка, из-за которой до
первого ответа сети можно листать в пустоту. Теперь `1`.

### 3. Скоуп экрана P2P-отправки не отменялся (`529942a`)

`scope` создавался через `remember { CoroutineScope(...) }`, а не
`rememberCoroutineScope()`, то есть отменять его должен был кто-то вручную. В
`DisposableEffect` стоял только `controller.stop()`, а он гасит свой `prepareJob`
и рекламу:

```kotlin
fun stop() {
    prepareJob?.cancel()
    nearby.stopAll()
}
```

Всё, что запущено на том же scope мимо контроллера, продолжало работать. Прежде
всего это упаковка бандла в `P2pSendPreparer`: уйти с экрана посреди подготовки
большого альбома L означало, что упаковка докрутится до конца, а прогресс
продолжит капать в `MutableStateFlow`. Остановить это было нечем до конца
процесса.

Контракт при этом записан прямо в документации `P2pSendPreparer` («scope —
область жизни экрана отправки»). Намерение задокументировано, код его не
выполнял.

Здесь же убран `!!` в `ScreenP2pReceive`. Ветвление

```kotlin
val state by if (activeController != null) {
    activeController!!.state.collectAsState()
} else { remember { mutableStateOf(ReceiveState.Idle) } }
```

работало — Compose корректно пересобирает группу при смене ветки, — но держалось
на неочевидном инварианте: между проверкой и `!!` не должно случиться
рекомпозиции. Подменять источник проще, чем ветку.

### 4. `collectAsState` без Lifecycle (`c17b907`)

Шесть мест против ста одиннадцати уже переведённых — то есть забытые остатки, а
не решение. Обычный `collectAsState` продолжает собирать поток, когда приложение
свёрнуто: список загрузок, история поиска, состояние профиля и список блокировок
обновлялись в фоне без нужды.

### 5. Проверка кода доступа считалась на главном потоке (`964592f`)

`verifyPassword` и `setPassword` — это 120 000 итераций PBKDF2-HmacSHA256, то
есть сотни миллисекунд на среднем телефоне. Вызывались синхронно: из колбэка
`AppLockScreen` и из диалога настроек. Экран замка показывается при каждом
запуске приложения, так что это была самая заметная заморозка в нём — без
индикатора и без защиты от повторного нажатия.

- обе функции стали `suspend` и считают хеш на `Dispatchers.Default`;
- `onUnlock` у `AppLockScreen` — `suspend`-лямбда;
- пока идёт проверка, повторное нажатие не запускает вторую.

Сам алгоритм не трогал: PBKDF2 с 16-байтовой солью из `SecureRandom`, сравнение
через `MessageDigest.isEqual`, персистентная экспоненциальная задержка после
четырёх ошибок — всё это сделано правильно. Добавлен только
`PBEKeySpec.clearPassword()` в `finally`.

### 6. Область FileProvider и настройки WebView (`16d67a5`)

`file_paths.xml` объявлял `<files-path path="." />` и `<cache-path path="." />` —
весь внутренний каталог приложения и весь кеш целиком. Дыры это не давало: права
выдаются по конкретному URI, а единственный вызывающий `useCaseShareFile`
передаёт конкретный файл. Но область была шире всего, чем приложение делится.
Осталось `store/` (журнал ошибок) и `cacheDir/L/Share`.

**WebView с включённым JavaScript** в `feature-x` — находка не моя, а lint'а,
который заработал в следующем коммите. В линзе безопасности я его пропустил:
грепал манифест и разрешения, а не исходники. Отключить JS нельзя — смысл этого
WebView в том, чтобы получить HTML после выполнения скриптов. Моста в приложение
нет: ни одного `@JavascriptInterface` не регистрируется. Добавлено
`allowContentAccess = false`, явный `MIXED_CONTENT_NEVER_ALLOW` и `@SuppressLint`
с объяснением вместо молчаливого предупреждения.

`AppContextHolder` помечен `@SuppressLint("StaticFieldLeak")`: `init()` кладёт
`applicationContext`, живущий столько же, сколько процесс.

### 7. Lint проверяет все модули, а не один `:app` (`b751bef`)

## Проверено и в порядке — не трогать

Места, куда линзы заглянули и не нашли, к чему придраться. Записано, чтобы
следующий проход не тратил на них время.

- **`AppLockRepository`** — PBKDF2-HmacSHA256, 120 000 итераций, 16-байтовая
  соль из `SecureRandom` на каждый пароль, `MessageDigest.isEqual` (постоянное
  время), персистентная экспоненциальная задержка с потолком 30 минут, убийство
  процесса её не сбрасывает. Заметно выше среднего.
- **`Repository` в L** — три раздельных мьютекса, LRU с потолком записей,
  `AtomicLong` для кулдауна с объяснением, почему не `@Volatile`. И проверка
  возраста ROM-кеша, которой не было в R: правильный образец лежал через модуль.
- **`MediaPlayerHost`** отменяет свой скоуп в `release()`.
- **Двойная проверка в `CoilImageLoaderFactory`** написана канонически:
  `@Volatile` на поле, повторная проверка под `synchronized`.
- **`network_security_config.xml`** — `cleartextTrafficPermitted="false"`,
  доверенные корни `system` плюс ISRG Root X1 для старых Android.
- **Манифест** — экспортирована только `SplashActivity` как лаунчер,
  `MainActivity` и `FileProvider` — `exported="false"`, разрешения геолокации
  ограничены `maxSdkVersion="32"`.
- **`proguard-rules.pro`** — правила выведены из реальных падений, каждое с
  объяснением; `-dontobfuscate` — осознанное решение владельца.
- **Учётные данные Luscious** — открытый пункт прохода 4 закрыт: в `Settings`
  используется `SettingElementSecureString`.
- **Тяжёлой работы в композиции** больше не нашлось: разбор URL превью обёрнут в
  `remember` с правильными ключами, запись `pageCountState` идёт из
  `LaunchedEffect`, лямбда `{ totalPages }` читает состояние при каждом вызове.

## Ложные находки этого дня

- **«В плеер уходит адрес `"null"`»** — нет, `UrlVideoLite` его отсеивает.
  Правка сделана по другой причине (см. проход 6, п. 1).
- **Дублирующиеся значения `Order`** — `NICHES_*` пары с одинаковым `value`
  выглядели как потерянное направление сортировки. Оказалось, эти константы
  используются только для сортировки на клиенте (`sortedBy` / `sortedByDescending`),
  а `value` у них не уходит никуда.
- **`getRefreshKey` с мёртвой веткой** — `closest?.prevKey?.plus(1)` никогда не
  срабатывает, потому что оба источника ставят `prevKey = null`. Верно, но ни на
  что не влияет: следом идёт рабочий `?: closest?.nextKey?.minus(1)`.
