## Находки

### T1 — Плеер X в свёрнутом приложении каждые 3 с перезаписывает запись истории. Низкая.

[VideoPlayerContentView.kt:208](../feature-x/src/main/java/com/client/xvideos/x/screens/videoplayer/molecule/VideoPlayerContentView.kt:208) ·
[LocalVideoPlayerContent.kt:90](../feature-x/src/main/java/com/client/xvideos/x/screens/videoplayer/molecule/LocalVideoPlayerContent.kt:90) ·
[SavedX_History.kt:102](../feature-x/src/main/java/com/client/xvideos/x/feature/saved/SavedX_History.kt:102)

Оба плеера X (сетевой и скачанного ролика) сохраняют прогресс циклом
`LaunchedEffect(host.isPaused)`: пока `isPaused == false`, каждые 3 с
вызывается `onSaveProgress`. А `isPaused` — пауза с экрана. Уход в фон
ставит на паузу только сам `ExoPlayer` (наблюдатель ядра снимает
`playWhenReady` на `ON_PAUSE` / `ON_STOP`), а `isPaused` не трогает.

Пока экран плеера открыт, а приложение свёрнуто или закрыто замком, цикл
работает дальше. Позиция не меняется, но запись всё равно происходит:
`savePlayerProgress` → `updateProgress` неизменившуюся позицию не отсеивает.
Каждый вызов делает три вещи:

- ставит новый `updatedAt`;
- атомарно переписывает файл записи (`FileDB.insert` → `writeTextAtomically`);
- на главном потоке переставляет запись в начало списка истории.

Видно это не на экране, а в расходе: запись во флеш раз в 3 с, 1200 раз в
час, сколько бы приложение ни висело свёрнутым с открытым плеером.

Воспроизведено на телефоне владельца на сборке `cc60313c` (рабочее дерево).
Настройки владельца, замок 30 с. Ролик X открыт, играет, «Домой». Время
изменения файла `files/store/X/History/<id>.XHistoryItem` читалось через
`run-as` раз в 2 с:

```
до «Домой»: mtime = сейчас (пока ролик играет, файл пишется раз в 3 с)
после «Домой»: t+2 → запись t+0, t+5 → t+3, t+7 → t+6, t+9 → t+9, … t+53 → t+51
через 3 мин в фоне: последняя запись 1–2 с назад, процесс жив, наверху рабочий стол
lastPositionMs в файле на 51-й секунде — 40183 (позиция не менялась)
экран плеера закрыт «Назад», «Домой» → через 10 с файл не менялся 14 с
```

HyperOS за три минуты процесс не заморозила, и запись не встала сама.

Чего у находки **нет**:

- расход батареи не мерился;
- загрузка процессора свёрнутым приложением мала и шумна: по `/proc/<pid>/stat`
  0,57 с и 0,01 с процессорного времени за два интервала по 10 с. Списать её
  на цикл нельзя.

У ленты R этого нет: она сохраняет не историю, а только время на экран, и
после правки C1 прохода 203 её цикл на снятом `playWhenReady` ждёт без
опроса.

Как чинить — на выбор владельца:

1. Крутить цикл сохранения только пока экран запущен
   (`repeatOnLifecycle(STARTED)` вокруг цикла или его аналог через
   `LifecycleStartEffect`) и сохранять один раз на уходе — как уже делает
   `onDispose`.
2. Не писать, если позиция с прошлой записи не изменилась: проверка в
   `updateProgress` против `historyMap[item.id]`. Цикл в фоне останется, но
   на диск и в список ходить перестанет.

## Правки

T1 исправлена по слову владельца после отчёта, вариантом 1 (`c223e376`). Правка
одинаковая в обоих плеерах X (`VideoPlayerContentView`,
`LocalVideoPlayerContent`):

- цикл сохранения раз в 3 с идёт внутри
  `lifecycleOwner.repeatOnLifecycle(STARTED)`. На `ON_STOP` он
  останавливается, на `ON_START` начинается заново с одной записи. Ключи
  эффекта — `isPaused` и `lifecycleOwner`;
- на уходе прогресс сохраняется один раз — `LifecycleEventEffect(ON_STOP)`;
- сохранение при закрытии экрана (`onDispose`) не трогалось.

Юнит-теста нет: это проводка эффектов в composable, а Compose-тестов в
проекте нет. Поведение проверено на телефоне (ниже). Число тестов не
изменилось, README не правится.

## Проверено, замечаний нет

- **Правка C1 (`cc60313c`).**
  - `awaitPlayWhenReady` вешает слушатель внутри
    `suspendCancellableCoroutine` на том же потоке, где проверила флаг, так
    что событие между проверкой и подпиской не теряется.
  - Повторные `onPlayWhenReadyChanged` после возобновления отсекает
    `continuation.isActive`.
  - Отмена до подписки тоже проходит через `finally`, и слушатель снимается.
  - Выход цикла по `!play` совпадает с прежним для паузы с экрана:
    `togglePlay` меняет `play`, а это ключ.
  - `PlayerControls.stop()` (снимает флаг и ставит позицию 0) в ленте R
    никто не вызывает. Если бы вызывали, цикл ждал бы так же, как раньше
    выходил: время 0 он отдал бы и тогда, и теперь только на следующем
    проходе.
  - Остальные ключи цикла (`player`, `mediaItem`, `isCurrentPage`, точки
    A-B) перезапускают его, как и раньше.
- **`68a3a124`** — перенос блока KDoc, текст не менялся.
- **Другие циклы** (`while (isActive)` / `while (true)` в `src/main`):
  - `CMPPlayer2` (X, L): выходит только по `config.isPause`, в фоне опрашивает
    позицию 20 раз в секунду, но колбэк зовёт лишь при её изменении. Дёшево.
    Свёрнутое приложение по `/proc` почти не грузит процессор (см. T1);
  - `NetworkTrafficMonitor`: раз в 2 с на весь процесс, читает `TrafficStats` —
    дёшево, не связано с экраном;
  - `CanvasTimeDurationLine` — обычный цикл жестов внутри `pointerInput`;
  - циклы чтения в `ZipUtils`, `XlrBackupManager`, `DownloadTask`,
    `LMediaPersist` и репозиториях L — потоковые, выходят по концу данных и с
    экраном не связаны. Ещё одно место — закомментированный код в
    `AppNetworkSpeedMonitorLite`.
- **Ключи по широким наборам.** Адрес плеера во время просмотра меняет
  только `downloadedKeys` у страницы ленты R — это C2 прохода 203, открыта.
  В «Избранном» и «Истории» X `remember(downloadedIds, …)` пересобирает
  адреса превью в сетке, а не адрес открытого плеера. На канале X
  `remember(downloadedVideoIds)` строит только признак «скачано».
