## Находки

### T1 — Карта прогресса загрузки картинок не очищается и растёт на каждую картинку из сети. Низкая.

[CoilProgressManager.kt:20](../core/src/main/java/com/client/xvideos/common/coil/CoilProgressManager.kt:20) ·
[CoilImageLoaderFactory.kt:65](../core/src/main/java/com/client/xvideos/common/coil/CoilImageLoaderFactory.kt:65)

`CoilProgressManager` — синглтон с `mutableStateMapOf<String,
CoilProgressItem>`. Сетевой перехватчик OkHttp у загрузчика Coil пишет в него
запись по адресу картинки на каждое чтение тела ответа. Удаляют записи только
`clear(url)` и `clearAll()`, а их в `src/main` никто не вызывает. Читает
карту один `UrlImage` — для своего адреса.

Итог: запись о каждой картинке, хоть раз скачанной по сети, живёт до конца
процесса. Это адрес и `CoilProgressItem`, плюс узлы неизменяемой карты. Сами
записи небольшие, но их число растёт без предела — с каждой страницей
миниатюр R, L и X. Кроме того, каждая порция ответа копирует путь в дереве
карты и рождает новую запись снимка.

Замерено на эмуляторе Pixel_10_Pro_Fold, сборка 17.10 (код карты, перехватчика
и `UrlImage` с тех пор не менялся: последний коммит в них — `9e27110a`,
25.09). Снимки памяти `am dumpheap -g` после принудительной сборки мусора.
Размер — поле `size` у `PersistentHashMap` в записях
`CoilProgressManager._progressMap`:

| Момент | Записей в карте |
| --- | --- |
| список альбомов L сразу после запуска | 14 |
| после четырёх страниц списка | 95 |
| ушли в главное меню (картинок на экране нет) | 95 |
| снова L, ещё шесть страниц, снова главное меню | 234 |

Чего у находки **нет**:

- память на запись не мерилась. По устройству записи (адрес на 100–200
  символов, объект прогресса, узлы дерева) это сотни байт, то есть порядка
  мегабайта на несколько тысяч картинок;
- на телефоне не проверялось: он отключился до замера.

Как чинить — на выбор владельца:

1. Убирать запись, когда загрузка закончилась (`done`) или когда `UrlImage`
   с этим адресом уходит из композиции.
2. Ограничить размер карты: держать только идущие загрузки.

### T2 — `UrlImage` перекомпонуется на каждую порцию загрузки своей картинки, троттлинг в 200 мс не работает. Низкая.

[UrlImage.kt:150](../core/src/main/java/com/client/xvideos/common/coil/UrlImage.kt:150) ·
[UrlImage.kt:163](../core/src/main/java/com/client/xvideos/common/coil/UrlImage.kt:163)

Прогресс картинки читается в два шага:

- `rawProgress` — `derivedStateOf` над записью карты из T1;
- `progress` — `produceState`, который по комментарию раз в 200 мс
  переносит значение `rawProgress` («Стало: подписка на snapshot-состояние с
  тем же троттлингом 200 мс»).

Но `rawProgress` передан в `produceState` начальным значением. Аргумент
вычисляется в теле composable при каждой перекомпоновке, значит, это чтение
состояния в композиции: `UrlImage` подписан на `rawProgress` напрямую.

Перехватчик пишет новую запись на каждое чтение тела ответа (обычно по 8 КБ),
и записи отличаются числом байт. Поэтому каждая порция снимает с `UrlImage`
этого адреса пропуск перекомпоновки. Получается одна перекомпоновка на
порцию: для миниатюры на 50–100 КБ это около десятка, для большой картинки
L на 2 МБ — порядка 250. Троттлинг в 200 мс ограничивает только обновление
`progress`, но не саму перекомпоновку. Подписка есть и тогда, когда
`needProgress == false` и прогресс картинке не нужен вовсе.

Чего у находки **нет**: вывод сделан по коду и по правилам Compose (чтение
состояния в теле composable подписывает его область). Число перекомпоновок
на устройстве не мерилось, подтормаживаний не наблюдалось.

Как чинить — на выбор владельца: начальное значение `produceState` брать без
чтения состояния. Например, `CoilProgressItem(url, 0, 0, false)`, а
`rawProgress` читать только внутри `snapshotFlow`. Тогда композицию будит
только `progress`, не чаще раза в 200 мс, и только когда прогресс нужен.

## Проверено, замечаний нет

- **Запись в карту T1 с нескольких сетевых потоков сразу** безопасна:
  `SnapshotStateMap` меняет запись в цикле с повтором под своим `sync`.
  Перекомпоновок у чужих картинок запись не вызывает. Композиция сверяет
  производное значение по `structuralEqualityPolicy`, и `UrlImage` будит
  только смена записи его адреса.
- **`AlbumPicsDetails` (L)** пишет `pics` и `failedPages` с потока `Default`.
  Это сделано намеренно: под мьютексом и внутри `Snapshot.withMutableSnapshot`.
  Других писателей у `pics` нет. Читатели на главном потоке делают
  `toList()` (атомарная копия через `toArray`) или читают в композиции.
- **Хранилища с записью через `withContext(Dispatchers.Main)`**:
  `SavedL_Collection`, `SavedL_Likes`, `AlbumTopHits`, `ExpandMenuVM`,
  `BlockRed`, `R_Saved_Collection`, `R_Saved_NichesCaches`,
  `R_Saved_Subscriptions` (чтение выбранного списка тоже уходит на главный),
  `BackupController` (главный диспетчер).
- **ScreenModel X и L** (`ScreenX_ChannelSM`, `ScreenXDashBoardsSM`,
  `ScreenTagsViewModel`, `ScreenX_ActressesIndexSM`, `ScreenX_VideoPlayerSM`,
  `ScreenLAlbumSM`, `ScreenAlbumListSM`): на IO и Default уходят только
  сеть, диск и разбор. Состояние пишется после возврата на поток
  вызывающего. `CountryState.updateCurrent` вызывается после
  `withContext(Default)`, то есть уже на главном.
- **Прогресс скачиваний R и X** (`Downloader.onVideoProgress`,
  `SavedX_Downloads.onVideoProgress`) пишется в `StateFlow` под
  `synchronized`, а не в снимковое состояние.
- **`R_Saved_NichesCaches.refresh`** вызывается и с IO (`refreshIfStale`), и
  с главного (кнопка). Проверка `isDownloading` и запись в него — две
  операции без блокировки. Но окно между ними — один вызов без задержек,
  попасть в него нажатием нельзя. В находки не идёт.
