## Новые находки

### UI1 — Состояние навигации хранится в статической переменной. Средняя.

[ScreenExplorer.kt:50](../feature-r/src/main/java/com/client/xvideos/r/ui/explorer/ScreenExplorer.kt)

```kotlin
class ScreenRedExplorer : Screen {
    companion object {
        var screenType by mutableIntStateOf(0)
    }
    // ...
}
```

Состояние выбранного таба (`screenType`) лежит в `companion object`.
Что из этого следует:
1. **Процесс смерти (Process Death):** При вытеснении приложения из памяти системой и последующем возврате, статические переменные сбрасываются. Пользователь, находившийся на вкладке поиска (3), после сворачивания и разворачивания приложения обнаружит себя на вкладке Gifs (0).
2. **Глобальность:** Если `ScreenRedExplorer` когда-либо появится в стеке дважды или будет переиспользован, обе копии будут делить один и тот же `screenType`, что приведет к непредсказуемому поведению UI.

*Как чинить:* Так как используется `Voyager`, состояние экрана следует держать либо внутри `ScreenModel`, либо использовать `rememberSaveable` на уровне `@Composable fun Content()`.

### UI2 — Отсутствие ScreenModel/ViewModel в большинстве фичей. Низкая.

Поиск по проекту показывает, что полноценный класс `ScreenModel` (от Voyager) или `ViewModel` используется только в единичных случаях (например, `ScreenTagsViewModel`, `ScreenSavedCollectionSM`).
В большинстве экранов вся бизнес-логика и хранение состояния размазаны по `@Composable` функциям или, как в пункте UI1, вынесены в `object`/`companion object`.

*Почему это проблема:* Смешивание логики получения данных и их отображения затрудняет тестирование и нарушает инкапсуляцию. В приложении с обилием асинхронных операций (сеть, файловая БД) это приводит к тому, что при перекомпозициях могут повторно срабатывать тяжелые запросы, если они не обернуты в `remember` или `LaunchedEffect` должным образом.

*Как чинить:* Использовать `ScreenModel` для каждого нетривиального экрана Voyager. Убрать логику из `@Composable`.
