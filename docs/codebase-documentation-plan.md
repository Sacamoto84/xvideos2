# План и спецификация сквозного документирования кодовой базы

**Дата создания:** 2026-09-26  
**Статус:** Согласовано (Brainstorming Complete)  
**Область действия:** `:core`, `:feature-l`, `:feature-r`, `:feature-x`, `:app`  
**Исключения (Non-Goals):** Compose UI (`@Composable`-верстка), P2P (пакеты и логика `p2p`)

---

## 1. Резюме понимания (Understanding Summary)

* **Проблема:** После прохождения 54+ раундов глубокого код-ревью и оптимизаций (v1–v270, более 1024 проходов) кодовая база существенно расширилась: добавлено множество валидационных предикатов, гвардов от 0-байтовых файлов, вспомогательных методов жизненного цикла, потокобезопасных кэшей и корутинных обработчиков. Когнитивная нагрузка при чтении кода возросла, требуется систематизировать и пояснить логику.
* **Цель:** Провести сквозное KDoc-документирование и комментирование кодовой базы, сделав понятным назначение каждого класса, интерфейса, метода, свойства и сложного блока логики для любого инженера.
* **Язык и стиль:** Русский язык. KDoc над декларациями (назначение, контекст использования, инварианты, `@param`, `@return`) + инлайн-комментарии (`//`) внутри сложных условий и ветвлений.
* **Охват:** Публичные контракты + нетривиальные `internal` и `private` элементы (кэши, атомики, потоки, вспомогательные функции).
* **Жёсткие ограничения:**
  * Compose UI не трогаем (файлы чистой верстки и `@Composable`-функции не модифицируются).
  * P2P не трогаем (пакеты `com/.../p2p/**` полностью исключены).
  * 0 изменений в исполняемом коде / семантике.
  * 0 предупреждений Detekt и 100% прохождение всех unit-тестов.

---

## 2. Зафиксированные предположения (Assumptions) & Риски

### Предположения:
1. `ScreenModel`/`ViewModel` и стейт-холдеры, находящиеся внутри пакетов `ui/`, относятся к presentation-логике и **входят** в скоуп документирования (в отличие от `@Composable`-функций).
2. Комментарии должны фокусироваться на вопросах **«зачем это нужно»** и **«каковы инварианты/ограничения»**, избегая очевидных тавтологий.
3. Существующие ценные комментарии сохраняются и органично интегрируются в KDoc.

### Риски и меры их снижения:
| Риск | Вероятность | Влияние | Мера снижения |
|---|---|---|---|
| Случайное повреждение логики или импортов | Низкая | Высокое | Автоматический аудит `git diff` перед фиксацией: разрешены только строки комментариев |
| Нарушение кодстайла Detekt | Средняя | Среднее | Запуск `./gradlew detekt` после каждого этапа (требование: 0 warnings) |
| Регрессия тестов | Низкая | Критическое | Запуск `./gradlew testDebugUnitTest` после каждого этапа (требование: 100% pass) |
| Затрагивание Compose UI или P2P | Низкая | Высокое | Фильтрация по путям файлов и AST/сигнатурам `@Composable` |

## 3. Журнал решений (Decision Log)

| № | Решение | Рассмотренные альтернативы | Обоснование |
|---|---|---|---|
| **D1** | Тотальное KDoc-документирование не-UI и не-P2P кода | Точечно только новые методы / Ключевые архитектурные узлы | Пользователю необходима полная прозрачность всей не-UI кодовой базы проекта |
| **D2** | Русский язык: KDoc + `//` для внутренней логики | Английский язык / Только компактные `//` | Соответствует существующему стилю проекта и снижает когнитивную нагрузку |
| **D3** | Охват public + нетривиальных internal/private | Только публичный API классов | Множество архитектурных решений из ревью сосредоточено во внутренней реализации |
| **D4** | Исключение только `@Composable` и файлов верстки | Полное исключение папок `ui/` | `ScreenModel` и стейт-холдеры содержат ключевую бизнес-логику экранов |
| **D5** | Стратегия реализации: «Снизу-вверх» по слоям (Вариант 1) | Пофичевый проход / Одномоментный пакет | Гарантирует последовательность контекста от фундамента к потребителям |

## 4. Архитектура и структура документирования

### 4.1. Стандарт KDoc
* **Классы / интерфейсы:**
  * Назначение и архитектурная зона ответственности.
  * Потокобезопасность (`MainThread`, `Dispatcher.IO`, синхронизация).
  * Жизненный цикл (Singleton, Factory, ScreenModel lifecycle).
* **Методы и свойства:**
  * Описание выполняемой операции / хранимого состояния.
  * Контекст ревью (Rationale) — почему этот метод был добавлен (защита от 0B, гонок и т.д.).
  * `@param`, `@return`, `@throws` для неочевидных параметров и краевых случаев.
* **Инлайн-комментарии (`//`):**
  * Пояснение корутинных операций (`withContext`, `supervisorScope`).
  * Пояснение граничных условий в ветвлениях (`if`, `when`).

### 4.2. Порядок выполнения по слоям

1. **Этап 1: Базовый слой `:core`**
   * Загрузка данных: `kdownloader` (`KDownloader`, `DownloadModel`, очереди, статусы).
   * Хранилище и безопасность: `storage`, `backup`, `crypto` (`StorageCleanupGate`, `XlrChunkedCrypto`).
   * Сетевой стек: `network`, `doh`, `connectivityObserver`.
   * База данных и общие утилиты: `database`, `model`, `utils` (`CollectionDB`, `FileDB`, `SafePath`).

2. **Этап 2: Data & Domain слой фичей (`:feature-r`, `:feature-x`, `:feature-l`)**
   * Сетевые API клиенты и парсеры (`RedApi`, Luscious GraphQL, HTML-парсеры).
   * Репозитории и менеджеры данных (`BlockRed`, фильтры, кэши ниш/тегов).
   * Доменные сущности, мапперы и валидаторы.

3. **Этап 3: Presentation Logic фичей**
   * `ScreenModel` и `ViewModel` (`ScreenRedFullScreenSM`, `ExpandMenuVM` и др.).
   * Стейт-холдеры, классы событий и интентов, управление плеерами вне верстки.

4. **Этап 4: Точка сборки и сервисы `:app`**
   * Инициализация приложения (`Application`, Koin-модули).
   * Фоновые воркеры `WorkManager` (`MediaDownloadWorker`).
   * Безопасность и блокировка (`AppLock`, калькулятор-маскировка).

## 5. Гейты качества (Quality Gates)

На каждом шаге реализации обязательны к выполнению проверки:
1. `git diff`: только добавление комментариев, 0 изменений кода, исключены `@Composable` и `p2p`.
2. `./gradlew detekt`: 0 предупреждений и ошибок.
3. `./gradlew testDebugUnitTest`: 100% прохождение всех юнит-тестов проекта.
