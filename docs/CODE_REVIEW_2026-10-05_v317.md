## Находки

C1 подтверждена логом устройства. Остальные — по чтению кода.

### C1 — Каталог ниш R перекачивается при каждом запуске. Средняя.

[feature-r/.../saved/R_Saved_NichesCaches.kt:155](../feature-r/src/main/java/com/client/xvideos/r/common/saved/R_Saved_NichesCaches.kt:155)

`refreshIfStale()` считает кэш устаревшим, если список в памяти пуст.
`SavedRed` зовёт его из `init`
([SavedRed.kt:67](../feature-r/src/main/java/com/client/xvideos/r/common/saved/SavedRed.kt:67))
сразу после асинхронного `readFromDisk()`: файл ещё не прочитан, список пуст.
Каждый холодный старт заново качает весь каталог — по запросу на страницу с
паузой 200 мс, — хотя файл кэша свежий и срок в 24 часа не истёк.

Подтверждение: в логе телефона за 05.10.2026 на двух запусках с разницей
18 минут стоит одна и та же строка — `R niches cache auto refresh: exists=true
size=0 ageHours=0`.

### T1 — Перечитывания блокировок публикуются без порядка. Средняя.

[feature-r/.../block/BlockRed.kt:59](../feature-r/src/main/java/com/client/xvideos/r/common/block/BlockRed.kt:59)

Каждая блокировка запускает свой `refresh()`, результат публикуется по мере
готовности. Пользователь блокирует два ролика подряд: первое чтение каталога
началось до записи второго файла, а закончилось после второго чтения — в
памяти набор без второго ролика, и он снова появляется в лентах до следующей
блокировки или перезапуска. `FileDB` от такой гонки защищён номером загрузки,
здесь защиты нет.

Чего у находки нет: не воспроизводилась. Окно тем шире, чем больше файлов
блокировок — см. A1.

### C2 — Лента подписок без сети показывает пустоту, а не ошибку. Средняя.

[feature-r/.../saved/R_Saved_Subscriptions.kt:200](../feature-r/src/main/java/com/client/xvideos/r/common/saved/R_Saved_Subscriptions.kt:200)

`refreshSubscription()` глотает сбой загрузки каждого автора и возвращает то,
что набралось;
[ItemSubscriptionsPagingSource.kt:24](../feature-r/src/main/java/com/client/xvideos/r/common/pagin/ItemSubscriptionsPagingSource.kt:24)
отдаёт это как успешную страницу. Без сети лента выглядит как «у авторов нет
роликов» — без сообщения и кнопки повтора. При сбое части запросов ролики этих
авторов молча отсутствуют.

### A1 — Каждая блокировка перечитывает все файлы блокировок. Низкая.

[feature-r/.../block/BlockRed.kt:134](../feature-r/src/main/java/com/client/xvideos/r/common/block/BlockRed.kt:134)

После записи одного файла `refresh()` обходит все папки авторов и разбирает
каждый файл. Изменённый элемент известен: его можно добавить в набор или убрать
без обхода диска — это же закрывает T1.

### A2 — Лента подписок грузит авторов строго по одному. Низкая.

[feature-r/.../saved/R_Saved_Subscriptions.kt:188](../feature-r/src/main/java/com/client/xvideos/r/common/saved/R_Saved_Subscriptions.kt:188)

Ролики выбранных авторов запрашиваются последовательно, лента появляется после
последнего ответа. Пятьдесят подписок — пятьдесят запросов подряд до первого
кадра.

### A3 — Любое изменение коллекции R перечитывает все коллекции. Низкая.

[feature-r/.../saved/R_Saved_Collection.kt:130](../feature-r/src/main/java/com/client/xvideos/r/common/saved/R_Saved_Collection.kt:130)

Добавление и удаление элемента, создание и удаление коллекции заканчиваются
`refreshCollectionList()`, который читает с диска все коллекции со всеми
элементами. В L такая же находка (A1 прохода 177) уже закрыта.

### T2 — Перечитывание лайков R может потерять свежий лайк. Низкая.

[feature-r/.../saved/R_Saved_Likes.kt:118](../feature-r/src/main/java/com/client/xvideos/r/common/saved/R_Saved_Likes.kt:118)

`refresh()` берёт снимок списка, очищает его в фоне и заменяет список целиком.
Лайк, добавленный между снимком и заменой, в новый список не попадает: файл
записан, но из памяти лайк пропадает до следующего перечитывания.

Чего у находки нет: не воспроизводилась; окно открывается, только когда очистка
что-то изменила.

### C3 — Разблокировка не проверяет, удалился ли файл. Низкая.

[feature-r/.../block/useCase/blockItem.kt:79](../feature-r/src/main/java/com/client/xvideos/r/common/block/useCase/blockItem.kt:79)

`unblockItem()` игнорирует результат `delete()` и возвращает успех. Файл не
удалился — пользователь видит «GIF разблокирован», а ролик остаётся
заблокированным.

### C4 — Снекбар ошибки ниш печатает имя класса исключения. Низкая.

[feature-r/.../saved/R_Saved_NichesCaches.kt:138](../feature-r/src/main/java/com/client/xvideos/r/common/saved/R_Saved_NichesCaches.kt:138)

### C5 — Адреса медиа с именем сайта пишутся в лог. Низкая.

### A4 — Состояние диалогов живёт в хранилищах данных. Низкая.

[feature-r/.../saved/R_Saved_Collection.kt:41](../feature-r/src/main/java/com/client/xvideos/r/common/saved/R_Saved_Collection.kt:41)

Хранилище коллекций и синглтон блокировок держат видимость диалогов и выбранный

обычное ненаблюдаемое поле `blockItem`, одноимённое с методом. Слой данных
зависит от рантайма Compose.

### A5 — Изменяемое поле в `@Stable`-классе внутри списка состояния. Низкая.

[feature-r/.../saved/R_Saved_Subscriptions.kt:28](../feature-r/src/main/java/com/client/xvideos/r/common/saved/R_Saved_Subscriptions.kt:28)

`SelectedCreator.select` — обычный `var`, элементы лежат в `mutableStateListOf`.
Присваивание на месте не вызовет рекомпозицию. Сейчас экран заменяет элемент
копией, дефект не проявляется; `val` исключил бы его.

### Проверено, находок нет

- **Запись блокировок.** Имена проверяются на выход из каталога, запись
  атомарная.
- **Обновление каталога ниш.** Сбой любой страницы обрывает обновление целиком:
  неполный список на диск не пишется.
- **Перечитывание коллекций.** Номер загрузки и отмена предыдущего чтения
  исключают публикацию устаревшего списка.
- **Отмена.** В ленте подписок отмена пробрасывается, цикл по авторам не
  продолжается на отменённой корутине.
