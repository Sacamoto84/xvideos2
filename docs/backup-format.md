# Бэкап: что сохраняется и как возвращается

Описывает `XlrBackupManager` (`:core`), экран «Настройки → Backup» и докачку
после восстановления. Проверено на устройстве 06.08.2026.

---

## 1. Где лежат данные приложения

Всё дерево — во внутренней памяти, в `filesDir/store`. Каталог недоступен
другим приложениям и файловым менеджерам, поэтому пароль на приложении
закрывает не только экраны, но и сами файлы. Обратная сторона: данные стираются
вместе с приложением, и единственный способ их сохранить — этот бэкап.

Пути задаются в `AppPath`:

```
filesDir/store/                    ← AppPath.main, корень бэкапа
├── X/
│   ├── Favorites/                 избранное X
│   ├── Download/                  скачанные видео X
│   ├── History/                   история просмотров
│   └── Subscriptions/             подписки на каналы и моделей
├── L/
│   ├── Likes/                     лайки L
│   ├── Collection/                коллекции L
│   └── Album/                     кеш альбомов
├── R/
│   ├── Download/                  скачанные гифки R
│   ├── Likes/                     лайки R
│   ├── Collection/                коллекции R
│   ├── Block/                     блокировки
│   ├── Niches/                    сохранённые ниши
│   ├── Creators/                  сохранённые авторы
│   └── Subscriptions/             подписки
├── DB/                            файловая база (кеши ответов)
├── inbox/  outbox/                временные каталоги P2P
└── crash.log                      журнал ошибок релизной сборки
```

**В бэкап идут только `X`, `L` и `R`.** `DB` — это кеши, они восстанавливаются
из сети; `inbox`/`outbox` — временные; `crash.log` к данным пользователя не
относится.

## 2. Из чего состоит элемент L

Это важно для понимания режима «Мини». Каждый лайк или элемент коллекции L —
**папка**, а не файл:

```
L/Likes/<альбом>_<хеш>/
├── metadata.json                  описание: адреса, размеры, теги, альбом
├── <имя>.jpg                      сам файл (или .mp4)
└── <имя>.<размер>.jpg             превью в нескольких размерах
```

В `metadata.json` лежат, среди прочего:

| поле | что это |
|---|---|
| `mediaFileName` | имя основного файла в этой же папке |
| `sourceMediaUrl` | адрес, откуда он был скачан |
| `previewFiles[]` | список превью: имя файла, `sourceUrl`, размеры |
| `picture` | полный объект `PicsDetails` с сайта |
| `albumId`, `albumTitle`, `albumDetails` | описание альбома |

У коллекции рядом с папками элементов лежит `collection.json` — обложка и
версия схемы.

---

## 3. Режимы «Мини» и «Полный»

Выбираются отдельно для L и для R. X всегда сохраняется целиком.

| режим | L (`Likes`, `Collection`) | R (`Download`) |
|---|---|---|
| **Полный** | всё: метаданные, картинки, видео, превью | все `.mp4` |
| **Мини** | только `metadata.json` и `collection.json` | только `.info` |

Отбор делает `shouldIncludeBackupEntry`. Логика простая: в режиме «Мини» из
папок L проходят лишь два имени файла, из `R/Download` — лишь расширение
`.info`. Всё остальное в архив не попадает.

Смысл: **мини-бэкап хранит не файлы, а ссылки на них.** Он на порядки меньше и
годится, чтобы перенести библиотеку на другое устройство. Полный — чтобы
сохранить то, что с сайта уже могли удалить.

## 4. Что внутри архива

Архив упаковывается в зашифрованный контейнер **`.xlr`** (`XlrChunkedCrypto`).
Снаружи файл представляет собой непрозрачный монолитный бинарный поток: ни имена файлов,
ни папки, ни размеры отдельных элементов невозможно прочитать без ввода пароля.

### Структура зашифрованного контейнера:
```
+--------------------------------------------------------------------------+
| ЗАГОЛОВОК (25 байт)                                                      |
| - Magic: 4 байта ("XLRB" = 0x58, 0x4C, 0x52, 0x42)                       |
| - Version: 1 байт (0x01)                                                 |
| - KDF Salt: 16 байт (SecureRandom)                                       |
| - Nonce Prefix: 4 байта (SecureRandom)                                   |
+--------------------------------------------------------------------------+
| ЧАНК 0 .. N (полезная нагрузка до 64 КБ)                                 |
| - isLast: 1 байт (0x00 или 0x01)                                         |
| - cipherLength: 4 байта Int (размер шифротекста + auth tag)              |
| - ciphertext + GCM Tag (16 байт): зашифрованный блок ZIP                 |
|   (Nonce: prefix[4] + chunkIndex[8], AAD: chunkIndex[8] + isLast[1])     |
+--------------------------------------------------------------------------+
```

* **Криптография:** Ключ выводится из введённого пользователем пароля через `PBKDF2WithHmacSHA256` (120 000 итераций) со случайной 16-байтной солью. Шифрование — `AES/GCM/NoPadding` (256 бит).
* **Потоковость (Чанки по 64 КБ):** Обработка стримовая, без загрузки архива в оперативную память, что исключает `OutOfMemoryError` при бэкапе гигабайтных видео.
* **Защита целостности (AEAD):** В AAD каждого чанка включается его порядковый номер и флаг `isLast`. Это исключает перестановку чанков местами, удаление чанков или обрезание файла (truncation attack). Неверный пароль определяется мгновенно на первом чанке.
* **Обратная совместимость:** Если архив начинается с сигнатуры `PK\x03\x04`, приложение определяет его как `LEGACY_ZIP` и позволяет восстановить без запроса пароля.

Внутри расшифрованного потока — ZIP-структура с `backup.json` в корне:

```json
{
  "schemaVersion": 1,
  "createdAt": "2026-08-06T19:25:27Z",
  "sections": ["X", "L", "R"],
  "paths": ["X", "L/Likes", "R/Download"],
  "modes": { "L": "MINI", "R": "FULL" }
}
```

Дальше — записи с путями относительно `store`, ровно теми, что перечислены в
`paths`. Имя файла по умолчанию: `xvideos-xlr-backup-YYYYMMDD-HHmmss.xlr`.

## 5. Как идёт создание

1. `currentBackupItems()` обходит `X`, `L`, `R` и считает по каждой папке число
   файлов и байт — с учётом выбранного режима. Отсюда галочки и размеры на
   экране.
2. Выбранные пути нормализуются: вложенный путь выкидывается, если выбран его
   родитель.
3. Пишется `backup.json`, затем каталоги — рекурсивно, с фильтром режима.

## 6. Как идёт восстановление

```
ZIP → проверка → распаковка во временную папку → перенос поверх данных → докачка
```

**Проверка (`validateBackup`).** Архив открывается и читается целиком, без
записи на диск: ищется `backup.json`, проверяется, что имена записей не
выходят за пределы корня (защита от zip-slip). Заодно собирается список папок
второго уровня, которые в архиве есть (`X/Favorites`, `L/Likes`).

**Какие папки трогаются (`XlrRestorePaths`).** Отметка раздела в дереве
означает «папки этого раздела, которые есть в архиве», а не раздел целиком.
Архив собирают и из части папок — например, X без загрузок, — и папка, о
которой архив ничего не знает, не трогается ни в одном режиме. Папка, которая в
архиве есть, но пуста, считается известной: при замене она станет пустой.

**Распаковка (`extractBackup`).** Только выбранные пути, во временную
`store/.xlr_restore_tmp`. Каждое имя нормализуется и проверяется `ensureInside`.

**Перенос (`applyRestoredPaths`).** Здесь важна последовательность:

1. текущая папка **не удаляется**, а переименовывается в `.xlr_old_<имя>`;
2. на её место переносится распакованная;
3. так по всем выбранным путям;
4. только когда перенесены все — прежние копии разбираются и удаляются.

Ошибка на любом шаге откатывает всё: перенесённое удаляется, отодвинутое
возвращается на место. Точка в начале `.xlr_old_` — чтобы копия, если процесс
убьют посреди работы, не выглядела как обычная папка данных.

**Режим (`XlrRestoreMode`).** Перед запуском экран спрашивает, что делать с
тем, чего в архиве нет:

| режим | что остаётся в папке после восстановления |
|---|---|
| «Заменить» | только содержимое архива; из прежней копии переезжают лишь скачанные медиа тех элементов, чьи метаданные пришли из архива (иначе после мини-бэкапа всё качалось бы заново) |
| «Объединить» | содержимое архива и всё прежнее, чего в архиве нет; запись, которая есть и там и там, берётся из архива |

Данные лежат по файлу или по папке на запись, поэтому объединение папок и есть
объединение списков. Разбор прежней копии — `XlrRestoreCleanup`, он идёт после
шага 4, когда откат уже не нужен. Остатки прерванных загрузок (`.temp`,
`.part`, `.tmp`) не переносятся.

**Журнал (`.xlr_restore_journal`).** Откат в коде не спасает, если процесс убит
посреди переноса. Поэтому в корне данных ведётся журнал: какие пути тронуты,
перенесено ли уже всё и в каком режиме шло восстановление. При следующем
запуске `recoverInterruptedRestore` либо возвращает прежние данные (перенос не
закончен), либо доводит разбор прежних копий в том же режиме. Пока след
прошлого восстановления не убран, новое не начинается.

**Обновление состояния в памяти.** Списки сохранённого живут в памяти и
читаются один раз, а восстановление меняет файлы мимо приложения. После него
перечитываются все три раздела: `SavedRed.refreshAll()`, `BlockRed.refresh()`
и список загрузок R, `SavedX.refreshAll()`, `SavedL.refreshAll()` — последний
вместе с содержимым коллекций, открытых за сеанс. Без этого раздел показывал
бы прежнее до перезапуска.

## 7. Докачка после мини-восстановления

Запускается автоматически, если среди восстановленных путей есть `L/Likes`,
`L/Collection` (`shouldAutoRecoverL`) или `R/Download`
(`shouldAutoRecoverRedDownload`).

Для L это `lRecoverIncompleteSavedMedia`:

1. обходит все `metadata.json`;
2. смотрит, каких файлов нет рядом с ними;
3. на каждый недостающий берёт записанный адрес и восстанавливает файл.

Решение «копировать или качать» принимается **по схеме адреса**:

| адрес | что делает |
|---|---|
| `http://` или `https://` | скачивает |
| всё остальное | считает локальным путём и копирует; если файла нет — ошибка |

Ход работы виден в консоли на экране восстановления (до 2000 строк).

### Что означают строки в консоли

| строка | значение | что делать |
|---|---|---|
| `L: media готово …` | файл скачан | — |
| `L: preview готово …` | превью скачано | — |
| `не скачан …: HTTP error: 410` | сервер удалил ресурс | ничего; элемент останется без файла, метаданные целы |
| `не скачан …: HTTP error: 4xx/5xx` | сетевая ошибка или блокировка | повторить позже |
| `не скачан …: исходный файл не найден: …` | в метаданных нет годного адреса | восстановить только из полного бэкапа |
| `L: нет URL для media …` | адрес в метаданных пуст | то же |

> Раньше на месте последней строки было `CLEARTEXT communication to localhost
> not permitted by network security policy`. Сообщение уводило в сторону:
> запрет открытого HTTP тут ни при чём. Локальный путь, файла по которому уже
> нет, попадал в сетевую ветку, ktor достраивал строку без схемы до
> `http://localhost/...` и упирался в политику. Исправлено 06.08.2026.

## 8. Что бэкап **не** сохраняет

- **Настройки приложения** — они в `SharedPreferences`, а не в `store`.
- **Код доступа** — хеш и соль лежат там же, в настройках.
- **Учётные данные L** — в зашифрованных настройках.
- **Кеши** (`DB/`) — восстанавливаются из сети сами.
- **Журнал ошибок** `crash.log`.

Отсюда: после восстановления на чистом устройстве нужно заново войти в L и
заново задать код доступа.

---

## 9. Ограничения, о которых стоит знать

**Мини-бэкап стареет.** Он хранит ссылки, а ресурсы на сайтах удаляют. Чем
старше архив, тем больше `410` при восстановлении. Если библиотека важна —
делать полный.

**«Заменить» стирает то, что появилось после бэкапа.** Папка, которая есть в
архиве, целиком заменяется его содержимым. Чтобы сохранить и новое, и архивное,
— режим «Объединить». Папки, которых в архиве нет, не меняются в обоих режимах.

**Времена папок бэкап не несёт.** Время изменения сохраняется только у файлов.
Порядок списков на это и опирается: списки X и R — на время файлов, лайки и
коллекции L — на `savedAt` из метаданных.

**Свободное место.** На время переноса на диске одновременно лежат: архив,
распакованная копия во временной папке и отодвинутая прежняя версия. Пик — до
трёх объёмов восстанавливаемых данных.
