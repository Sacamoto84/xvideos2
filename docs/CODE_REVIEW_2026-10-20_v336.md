## Находки

### C1 — После ухода из приложения в полноэкранной ленте R стоит время, а петля A-B не работает. Средняя.

[RedPooledVideoPlayer.kt:214](../feature-r/src/main/java/com/client/xvideos/r/ui/video/RedPooledVideoPlayer.kt:214) ·
[RedPooledVideoPlayer.kt:240](../feature-r/src/main/java/com/client/xvideos/r/ui/video/RedPooledVideoPlayer.kt:240)

Время ролика и петлю A-B ведёт один цикл: `LaunchedEffect` с опросом
каждые 50 мс. Он выходит по условию `!play || !exo.playWhenReady`. Вторая
половина условия срабатывает не только на паузе пользователя:

- `LifecycleStartEffect` той же страницы снимает `playWhenReady` на
  `ON_STOP`;
- то же делает смена ключа замка — при закрытом сеансе и при свёрнутом
  приложении с включённой «Защитой в диспетчере задач».

При возврате `ON_START` снова ставит `playWhenReady = true`, и ролик
играет. А цикл уже вышел. Его ключи (`player`, `mediaItem`, `isCurrentPage`,
`enableAB`, `timeA`, `timeB`, `play`) от ухода и возврата не меняются,
поэтому заново он не запускается.

Что видит пользователь:

- время внизу экрана стоит;
- петля A-B не работает: ролик доигрывает до конца и начинается с нуля.
  Перемотка на точку A живёт только внутри этого цикла;
- точки A и B ставятся по застывшему времени: `setTimeA` и `setTimeB`
  берут `currentPlayerTime`, который пишет только этот цикл.

Оживает всё после свайпа на другой ролик или после паузы и снова
воспроизведения: `play` в ключах. Условие на `playWhenReady` появилось в
`e0d67b27` (29.09).

Воспроизведено на телефоне владельца на сборке среза. Ролик ленты R
длиной 14 с, «Домой», через 3 с возврат интентом запуска. Замок не
сработал: срок 30 с. Время — подпись текущей позиции по `uiautomator dump`,
состояние плеера — `dumpsys audio`:

```
до ухода:        00:09 → 00:10 за 3 с, AudioTrack started
после возврата:  00:11 → 00:11 за 3 с, started
                 00:11 → 00:11, started   (ещё три замера по 3 с —
                 00:11 → 00:11, started    всё время 00:11 при ролике
                 00:11 → 00:11, started    длиной 14 с)
```

Чего у находки **нет**: петля A-B на устройстве не включалась. То, что она
перестаёт работать, выведено из кода: проверка `position >= timeB` и
перемотка на A стоят только в этом цикле.

У X и L этой ошибки нет: цикл `CMPPlayer2` выходит только по
`config.isPause`.

Как чинить — на выбор владельца:

1. Не выходить на снятом `playWhenReady`, а ждать, пока его снова поставят:
   `suspendCancellableCoroutine` со слушателем `onPlayWhenReadyChanged`.
   На паузе цикл спит, после возврата продолжает.
2. Выходить только по `!play`. Цена: опрос 20 Гц на текущей странице, пока
   приложение свёрнуто, — сейчас так работает `CMPPlayer2`.

### C2 — Ролик в полноэкранной ленте R начинается заново, когда закончилось его скачивание. Низкая.

[RedFullScreenPage.kt:34](../feature-r/src/main/java/com/client/xvideos/r/ui/fullscreen/molecule/RedFullScreenPage.kt:34)

Адрес страницы считается так:
`remember(item.id, item.userName, downloadedKeys) { redVideoUrl(...) }`.
Скачанный ролик играет из файла, остальные — по HLS. Цепочка такая:

1. Пользователь выбирает «Download» в меню ролика, который смотрит.
2. Когда скачивание закончилось, `refreshDownloadList` обновляет
   `downloadedVideoKeys`.
3. У страницы меняется адрес, за ним `MediaItem` — а это ключ
   `rememberPooledPlayer`.
4. Библиотека возвращает плеер в пул (`yield`: `stop()`,
   `clearMediaItems()`) и берёт его заново.
5. `playerSetup` ставит новый источник, и ролик стартует с нуля — после
   спиннера загрузки.

То же на одиночном экране (`RedFullScreenSingle`). Обратный переход — при
удалении скачанного ролика.

Недокачанный файл в набор не попадает: загрузчик пишет во временный `.temp`
и переименовывает его в конце, а `refreshDownloadList` берёт только `.mp4`.

Чего у находки **нет**: на устройстве не воспроизводилась. Для этого
пришлось бы скачать ролик на телефон владельца, а убрать скачанное потом
можно только удалением его данных. Вывод сделан по коду страницы и по
исходникам `rememberPooledPlayer` (`DisposableEffect(mediaItem, playerPool)`)
и `PlayerPool.yield`.

Как чинить — на выбор владельца:

1. Не менять адрес страницы, пока она на экране: считать его по
   `downloadedKeys` при входе страницы, без ключа в `remember`. Файл
   заиграет при следующем открытии ролика.
2. Запоминать позицию перед сменой источника и ставить её после
   `prepare()`.

## Правки

По слову владельца после отчёта исправлены C1 — вариантом 1 (`cc60313c`) и
A1 (`68a3a124`). Число тестов в README — `7f7a3194`. C2 ждёт решения.

**C1.** В `RedPooledVideoPlayer.kt` появилась функция
`Player.awaitPlayWhenReady()`. Пока `playWhenReady` снят, она держит
корутину без опроса: подписывается на `onPlayWhenReadyChanged` и
продолжает, когда флаг снова `true`. Слушатель снимается в `finally`, то
есть на потоке корутины, — и при отмене тоже.

В цикле времени выход теперь только по `!play`, то есть по паузе с экрана:
её снятие меняет ключ, и цикл стартует заново. На снятом `playWhenReady`
цикл не выходит, а ждёт — так он переживает уход в фон и замок. Комментарий
про `mediaItem` в ключах переписан: прежняя причина («цикл выходит, увидев
снятый `playWhenReady`») больше не верна.

Тесты (+3 в `RedPooledVideoPlayerTest`):

- если плеер уже играет, функция возвращается сразу и слушателя не
  оставляет;
- на `false` ждёт, на `true` продолжает и снимает слушатель;
- при отмене снимает слушатель.

До правки тест не собирался (`Unresolved reference 'awaitPlayWhenReady'`).

**A1.** Описание «Держать ли кодеки прогретыми…» перенесено к
`setForegroundMode`, текст не менялся.

## Проверено, замечаний нет

- **Ёмкость пула.** В KDoc `DEFAULT_POOL_CAPACITY` сказано, что
  `beyondViewportPageCount = 1` даёт три страницы. В покое это так. Пока
  палец тянет ленту, видны две страницы, и с соседями по краям живут
  четыре. Четвёртая ждёт плеер в `PlayerPool.acquire()` (канал `receive`).
  Это крайняя невидимая страница, и плеер она получает, как только лента
  встанет.
  - Потерять плеер пул может только так: отдал его ждущей странице, и в
    том же кадре, до того как она возобновилась, её убрали из композиции.
    Канал без `onUndeliveredElement` такой элемент роняет.
  - При обычном листании окно страниц сдвигается за кадр на одну: сдача
    плеера и уход ждущей страницы в один кадр не попадают. Программных
    прыжков `scrollToPage` в ленте нет.
  - В отчёт как находка не идёт: не воспроизведено, и сценария, который к
    этому ведёт, не найдено.
- **`SlidingWindowEffect`** (Media3). Пустое окно при первом кадре, пока
  список ещё не пришёл, разбирает ветка `else`: окно строится, как только
  `itemCount` стал больше нуля. Колбэки обёрнуты в `rememberUpdatedState`.
  В лямбдах ленты `downloadedKeys` — делегат состояния, так что значение
  читается в момент вызова, а не из первой композиции.
- **Реестр прогрева.** `track` даёт `None`, `Add` или `Replace` по
  равенству элементов. `Replace` снимает старый источник до добавления
  нового, `forget` снимает элемент, который запомнен, а не собран заново.
  Покрыто тестами `FeedPreloadRegistryTest` и `FeedPreloadPolicyTest`.
  - Если ролик ушёл из списка (заблокирован), индексы окна за ним
    сдвигаются, а реестр держит прежние элементы. Прогрев этих индексов
    греет не те ролики. Страница это исправляет сама (`mediaSourceFor` →
    `Replace`), остаётся лишний трафик — не дефект.
- **Порядок освобождения.** В `rememberFeedPlayerState` эффект
  освобождения объявлен первым, поэтому снимается последним:
  `setForegroundMode(false)` приходит на живой пул.
- **Адреса для прогрева и для страницы** считает одна функция
  (`redVideoUrl`), ключи менеджера прогрева совпадают с тем, что играет
  плеер.
- **Кнопка «Download» в меню ролика** есть и в полноэкранной ленте
  (`ExpandMenuVideo` из `RedFullScreenPageOverlay`). Поэтому C2 — сценарий
  из обычного пользования, а не из сетки.
