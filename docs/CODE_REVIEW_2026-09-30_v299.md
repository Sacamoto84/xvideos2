## 1. Контекст и цели реализации

В рамках масштабной инициативы по повышению читаемости, модульности и снижению когнитивной сложности кодовой базы был проведён полный архитектурный рефакторинг всех Jetpack Compose экранов и компонентов приложения. В правила проекта ([`GEMINI.md`](../GEMINI.md)) был добавлен и реализован жесткий архитектурный регламент:

1. **Принцип «Один компонент — один файл»:**
   - Каждая независимая `@Composable` функция вынесена в собственный `.kt`-файл.
   - Имя файла строго совпадает с именем функции (`ChannelSortBar.kt` -> `@Composable fun ChannelSortBar`).
2. **Запрет монолитных экранов (Hard Gate на код-ревью):**
   - В корневом файле экрана (`Screen<Name>.kt`) размещаются исключительно:
     - Voyager-класс экрана `class Screen<Name> : Screen`.
     - Привязка `ScreenModel`, подписка на `StateFlow`/состояния и маппинг навигационных колбэков.
     - Корневая функция компоновки экрана (`@Composable fun Screen<Name>Content`), которая только собирает готовые молекулы и макет верхнего уровня.
   - Все приватные, секционные и вспомогательные функции вынесены в поддиректории `atom/` или `molecule/`.
3. **Классификация компонентов:**
   - **`atom/`**: Неделимые базовые примитивы без вложенных кастомных виджетов экрана (чипы, аватары, бейджи, кнопки, плашки таймингов, элементы строк).
   - **`molecule/`**: Составные блоки, собирающие несколько атомов или реализующие функциональную секцию экрана (карточка видео/альбома, шапка профиля, строка поиска, панель фильтров, диалоги).
4. **Обязательные легковесные `@Preview`:**
   - Каждый файл в `atom/` и `molecule/` обязан содержать изолированную превью-функцию для мгновенного рендеринга в IDE.

## 3. Находки и устранённые замечания в процессе рефакторинга

### D1 — Правило Detekt `LongParameterList` при декомпозиции экранов. Высокая серьёзность.
- **Проблема:** При выносе крупных секций экранов с большим числом параметров (коллбэки, флаги, счетчики) линтер Detekt блокировал сборку правилом `LongParameterList` (лимит 12 параметров).
- **Решение:** Для сложных экранов введены компактные `@Immutable` структуры состояния (например, `SubscribedAlbumsUiState`, `FullScreenUiState`, `AlbumListUiState`, `SettingsDetailParams`), инкапсулирующие аргументы и повышающие стабильность Compose-рекомпозиции.
- **Статус:** Закрыт.

---

### D2 — Правило Detekt `MatchingDeclarationName` для извлечённых типов. Высокая серьёзность.
- **Проблема:** Размещение вспомогательных классов, интерфейсов или моделей в файлах с именем Composable-компонента нарушало требование совпадения имени файла и верхнеуровневого класса.
- **Решение:** Все вспомогательные структуры данных (`CollectionDialogData`, `DefaultPagerState1`, `HapticItem`, `SettingsPage`, `ScreenRootSM`, `AppSettingsSM`) вынесены в отдельные файлы с идентичным наименованием.
- **Статус:** Закрыт.

---

### D3 — Чистота импортов (`UnusedImports`). Высокая серьёзность.
- **Проблема:** В результате перемещения десятков Composable-функций в исходных файлах экранов оставались неиспользуемые импорты, нарушающие проверки Detekt.
- **Решение:** Проведён сквозной аудит и очистка импортов во всех модулях проекта.
- **Статус:** Закрыт.

---

### U1 — Сохранение UI-контрактов для автотестов (`testTag`). Высокая серьёзность (UX/Testing).
- **Проблема:** Риск потери `Modifier.testTag(...)` при переносе кнопок выбора раздела, строк ввода и элементов списков.
- **Решение:** Проверены и строго сохранены все тестовые теги (включая `"buttonL"`, поисковые теги и идентификаторы элементов навигации).
- **Статус:** Закрыт.

---

### P1 — Обеспечение 100% покрытия `@Preview` без тяжелых обёрток. Позитивное изменение.
- **Анализ:** Каждый новый компонент в папках `atom/` и `molecule/` снабжен изолированной превью-функцией с синтетическими данными по умолчанию, что позволяет мгновенно валидировать верстку без запуска эмулятора.
- **Статус:** Принято.
